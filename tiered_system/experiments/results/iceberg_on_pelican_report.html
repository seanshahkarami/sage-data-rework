Sage data pipeline · storage architecture

Iceberg on Pelican

We can run Apache Iceberg over Pelican and NRDStor. The catalog cannot live on object storage, concurrency is mandatory on the read side, and latency is not what separates Iceberg from a custom catalog.

The verdict

Pelican is good storage and a bad catalog

Every data file and every metadata file sits on Pelican without trouble. The one thing that does not work there is the commit: a filesystem catalog needs an atomic pointer swap, and the origin does not provide one. Tested directly, three of four concurrent writers were told they had won and two acknowledged commits were lost with nothing on storage recording that they should exist.

The design in plans/6 moves only that one responsibility off storage. Writers commit through an Iceberg SQL catalog, which arbitrates them; a single reconciler publishes metadata/version-hint.text to Pelican from the committed head; consumers read the hint and never open the database. A lost race under that design makes readers stale, not lossy, and the database still holds the true head, so it is repairable. It ran end to end on NRDStor with two concurrent committers, one reconciler and one database-less reader.

The planned cadence is monthly — data accumulates in InfluxDB, a month is committed to cold storage as one batch, then dropped from hot. That is twelve commits a year, and it makes most of the write-side costs below vanish: ~0.3 minutes of commit traffic per year, and 6.4 MB of accumulated metadata per decade. Several numbers in this report were projected against faster cadences before that was settled; they are kept where they show how a cost behaves, and labelled where they are not what we will pay.

Writing · exp37, 12/12

The write path is flat, and batching is the whole lever

Per-commit request count does not move as files accumulate. The bill is set by the number of commits, not by the size of the table.

At the monthly cadence we plan, the commit path effectively disappears: a third of a minute a year. The monthly job’s wall time is all data movement — roughly 10 GB a month, 4–6 minutes at the throughput measured below, plus the timestamp rewrite — and none of it is Iceberg.

The reconciler costs 2 requests to publish a hint and 1 to confirm it unchanged, regardless of table size. It stays negligible at any scale, so the reconciler period is bounded by how often we commit, not by what a pass costs.

Reading · exp37, 12/12

The read path is the expensive side, and one third of it is ours

The HEAD before every file is our bug, not Iceberg's

Our PelicanInputFile issues a HEAD to ask the origin for a size the manifest already records in file_size_in_bytes. It caches that size per instance, but pyiceberg builds a fresh instance for every file in every scan, so the cache never survives. A process-wide cache took the same read from 205 requests to 122 — 40% fewer, every HEAD gone. The two remaining GETs per file are the parquet footer and then the row group, which is Iceberg's correct access pattern.

Partition pruning was re-checked in requests against the origin rather than in files: a 60-partition table went from 302 requests and 2.1 s for a full scan to 37 requests and 0.8 s for a one-week filter, 88% fewer. Pruning, not a faster origin, is what makes the read path work. An unpruned full scan should be treated as a misuse of this deployment and documented as one.

A sequential Iceberg scan over Pelican runs at roughly 5 MB/s. At that rate a one-week query takes 9 minutes. With 8 to 16 workers it takes about one minute. Nothing in the default configuration hints at this.

pyiceberg already parallelises — it maps scan tasks onto a thread pool — so the 6.5–8.7× speedup needs no code, only PYICEBERG_MAX_WORKERS. Two details matter. The pool is over files, so a query touching one file gets nothing from it, which is a second independent reason to batch commits by day: it sets how many files a day-range query can spread across. And the executor is cached per process, so the variable has to be set before the first scan.

Treat 30 MB/s as the dependable figure. Run A was still gaining at 16 workers, run B had saturated, so anything above 30 is headroom rather than budget.

Column projection saves bytes but not time

Reading one column instead of all thirteen moved 94% fewer bytes and took only 43% less time — while issuing 20 more requests. A projected scan stops streaming bulk bytes and starts scattering small column reads, so it becomes latency-bound. Size a query by round trips, not by bytes.

Storage · exp40, 5/5

Iceberg's metadata costs 2.5 MB. The migration saves 35 GB.

The overhead has two shapes and conflating them gives a wrong answer. Manifest entries scale with data files; metadata.json scales with commits and embeds the entire snapshot history each time.

Measured on files holding real archive rows, because manifest entries store per-column bounds and the archive's string columns set their width.

The part people picture when they ask this question is the first one, and it is negligible: 4,564 files at 545 B is 2.5 MB of manifests for a 209 GB archive, or 0.0012%. Per-file metadata overhead is effectively zero.

The honest headline is a saving, not a cost

Ingest cannot register the archive in place, so every file is rewritten — and the rewrite stores 83% of on-disk size. The re-encode recovers four orders of magnitude more space than the metadata consumes. The caveat worth stating plainly: this is a property of re-encoding with current parquet defaults, not of Iceberg. Writing the same files with the same encoder and no catalog would save the same 35 GB.

Where storage can run away is retention, not file count. Keeping every metadata.json is quadratic, because each new version embeds the whole snapshot history. At 40 commits the retained versions were already 71% of all metadata bytes.

Cadence decides whether any of this matters, and ours is monthly — a month accumulates in InfluxDB, is committed to cold storage as one batch, then dropped from hot. At twelve commits a year the quadratic never gets going: 6.4 MB of retained metadata after a decade, against roughly a terabyte of data. The faster cadences are shown because they are what the mechanism costs if the design ever moves — at hourly commits it reaches 16% of the data archive just to describe it.

Snapshot expiry does not reclaim this, and we had assumed it did

Our design notes recorded "set a snapshot-retention policy" as the answer to unbounded metadata. Measured, it is not. expire_snapshots() rewrites history into a new metadata file and leaves every old one on disk: the current file shrank 72%, which is a real saving on every read, while stored bytes went up 1%.

ActionCurrent file (per read)All retained (storage)
expire_snapshots()34,318 → 9,531 B (−72%)717,930 → 727,461 B (+1%)
delete-after-commit, keep 5—718,068 → 154,986 B (−78%)

The only knob that reclaims stored metadata is write.metadata.delete-after-commit.enabled, which the design deliberately keeps off so a published hint can never name a deleted file. Expiry is still worth turning on — but for the read cost, not for storage.

The retention window, and why we are not using it

Retention itself is built into Iceberg — two stock table properties, 41 files and 716 KB down to 6 files and 155 KB. There is nothing for us to build. Two measured details decide whether we should.

First, the window counts versions, not time: twenty commits inside one second left six metadata files, and pyiceberg 0.12 has no age-based option for them. So the safe setting tracks the commit rate — “keep 5” is five hours at hourly commits, five days at daily ones, five months at monthly.

Second, the hint failure is real and exact. With previous-versions-max=5, a published hint’s target was deleted after commit #7 and a consumer following it got FileNotFoundError — a hard break, not the recoverable staleness this design accepts. The break point was previous-versions-max + 2 at every window tested (2→#4, 5→#7, 10→#12), which turns the sizing question into arithmetic: previous-versions-max > commits per reconciler period + margin.

At monthly commits, leave retention off

Not provisionally, and not pending a decision. The growth it would bound is 6.4 MB per decade — less than one month’s manifests — while turning it on introduces the failure mode above. The default previous-versions-max=100 already carries about 8.4 years of margin at this cadence, against a reconciler that republishes in minutes. Pin both properties explicitly rather than inheriting them, so a library upgrade cannot change the behaviour quietly. measured

What would reopen this: a cadence change. The window is count-based, so the conclusion follows from twelve commits a year, not from the design. At daily commits the margin is still months; at hourly, both the growth and the hint risk become real.

One related finding, harmless today. Expiry does not delete data files either: on an append-only table, expiring 7 of 8 snapshots removed no data files and no manifests. But after a delete or a compaction pass, superseded files stay on storage unreferenced — measured, 4 of 8 orphaned — and pyiceberg 0.12 ships no orphan cleanup. Sage's pipeline is append-only, so this costs nothing now. It becomes a prerequisite before compaction.

Batching pays here too. The same 32 files committed one at a time produced 765,779 B of metadata; committed together, 23,746 B — 32× less for identical data. Day-batching was already justified on request count and on read parallelism. This is a third, independent reason, and it is what keeps the quadratic above harmless.

The comparison · exp39, 5/5

Latency does not choose between Iceberg and the custom catalog

Iceberg's metadata layer sits between a consumer and the bytes, and its write path re-encodes every file. The obvious question is what that costs. We ported the custom catalog's store to Pelican and ran both designs over the same files, the same origin, the same FileIO, in the same process, interleaved.

Both readers pinned to 8 workers. Lower is better; a ratio under 1.0 favours Iceberg.
OperationIcebergCustomRatio
Write 4 files (169 MB)23.9 s25.2 s0.95×

Read one day2.9 s3.6 s0.8×

The prediction going in was that Iceberg's mandatory nanosecond-to-microsecond rewrite would make its write visibly slower. That hypothesis was refuted. Both paths are network-bound at about 6 MB/s, and the rewrite shrinks the payload 17%, so Iceberg's extra CPU hides behind an upload with less to send. Across runs the wall ratio ranged 0.86–1.05: the run-to-run spread on this link is larger than the difference between the designs.

Iceberg's 12 metadata requests against the custom catalog's 2 sounds like a 6× penalty and is not, because neither grows with file count. At 24 data files Iceberg is already down to 0.50 metadata requests per data file and still falling. Any query big enough to care about latency amortises it away.

One place the custom catalog scales worse

Its snapshot JSON embeds every live file at 167 bytes each, so at the archive's 4,564 files it reaches about 0.8 MB, downloaded in full by every reader on every read, and unprunable. That is smaller per file than Iceberg's 545 B of manifest, and the size was never the problem: Iceberg splits the same information across metadata.json and per-partition manifests, so a pruned reader fetches a fraction of its 2.5 MB while a custom-catalog reader fetches all 0.8 MB every time. Smaller total, worse access pattern. Both designs have an O(files) metadata structure; the difference is that Iceberg's is partitioned. Solvable on the custom side with per-day snapshot shards, but that is work which does not exist today.

A method note worth keeping

The first run showed Iceberg reading 3× faster. That was not a finding. pyiceberg's scan is parallel and our custom reader was a sequential for loop, so we were timing a loop against a thread pool. The throughput work above had just established that this difference alone is worth 6–8×, which is what made the result recognisable as an artefact. Both readers are now pinned to the same width and the gap disappeared.

Where the decision actually sits

A genuine trade, not a landslide

Our recommendation document still recommends building the custom catalog, and nothing measured here disturbs the reasoning behind it. What the measurements do is change the list of arguments. "Iceberg is slower" comes off the list as unsupported. A new liability goes on the custom side: the unprunable snapshot JSON. Everything else stands where it was.

Argues for IcebergArgues for the custom catalog
Concurrency safety — the custom catalog lost an acknowledged update silently, 3 of 3 attempts Smaller operational surface — no database, no reconciler to keep alive
Row-level deletes No nanosecond constraint — it indexes files as written and never reinterprets types
Ecosystem and external readers No mandatory rewrite on ingest
Partitioned metadata that a pruned reader can skip —

The decision rests on safety and operations, which are judgement calls about how Sage runs, not measurements. Whichever way it goes, the exporter fix comes first: a catalog over unprunable files just plans faster toward reading 49 MB to return one row.

Open risks, ranked

What could still bite us

1

Reconciler failure is silent

A consumer pointed at a stale hint returns an older snapshot with no warning, while a newer metadata file sits beside it in the same directory. The data is never lost and the database still holds the true head, but detection has to be active: the reconciler comparing the published hint against metadata_location. Nothing notices on its own.

2

We have not decided whether committers run on separate hosts

This is the only question that forces Postgres over SQLite, and it is unanswered. SQLite is sufficient for everything we measured; the constraint is connectivity, not concurrency. Default to SQLite until someone says yes.

3

A monthly job is the kind that gets re-run by hand

Committing once a month makes almost every cost here disappear, but it concentrates the whole year’s ingest into twelve long-running jobs — and infrequent jobs are the ones an operator re-runs manually after a failure. The SQL catalog arbitrates concurrent committers correctly, so this is survivable where a filesystem catalog would lose commits silently. It still deserves a real guard: a lock or a single-replica deployment, not a convention that the job only runs once.

4

A consumer on default settings is 6–8× slow

Nothing surfaces this. It looks like Pelican being slow rather than a thread pool sized to one.

5

Every number here came from one process on a laptop link

Concurrent readers, NRDStor under load, and whether 30–39 MB/s holds from a well-connected host are all unmeasured. The shape of the findings transfers; the absolute rates do not.
